# IndustrialTech: правила для AI-ассистентов

Этот файл является кратким входным контекстом для Claude, Copilot и других AI-инструментов. Перед изменением кода прочитайте также:

- [`AI_CONTEXT.md`](./AI_CONTEXT.md) — актуальная карта проекта и ограничения.
- [`ARCHITECTURE.md`](./ARCHITECTURE.md) — устройство модулей и основные потоки данных.
- [`DEVELOPMENT.md`](./DEVELOPMENT.md) — команды сборки, запуска и проверки.

## Правила работы

- Документацию вести на русском языке, сохраняя английские имена API, классов, методов и Gradle-задач.
- Перед реализацией кратко сформулировать план и затронутые файлы, затем самостоятельно выполнить изменение и проверки без дополнительного подтверждения плана.
- Все подсистемы (`main`, `ae`, `crafting`, `ore`) считать равноприоритетными; не предполагать, что задача относится к AE2 только из-за размера этого sourceSet.
- Не создавать коммиты, ветки или pull request без отдельной прямой просьбы пользователя.
- Перед началом работы проверить `git status --short` и не удалять, не откатывать и не перезаписывать незакоммиченные изменения пользователя.
- Если требование неоднозначно или меняет игровое поведение, баланс либо архитектуру, остановиться и задать один конкретный вопрос до редактирования файлов.
- После изменений сообщить изменённые файлы, выполненные проверки и их результат; отдельно отметить непроверенные сценарии и оставшиеся риски.

1. Не считать `build/`, `run/`, `run-data/`, `.gradle/` и `.idea/` исходным кодом. Это сгенерированные или локальные данные.
2. Не удалять и не откатывать незакоммиченные изменения пользователя. Перед правкой проверять `git status`.
3. Для Java сначала искать классы и методы через Java LSP, а затем читать только нужный диапазон файла.
4. Сохранять разделение `sourceSet`-ов: `main`, `ae`, `crafting`, `ore` и соответствующих `datagen*`.
5. Не переносить классы между `sourceSet`-ами без проверки classpath и регистрации Forge-мода.
6. Для регистрации блоков, предметов, меню и block entity использовать существующий паттерн `DeferredRegister` в соответствующем `init`-классе.
7. Для AE2-хранилищ учитывать одновременно AE API, Forge capabilities, серверную синхронизацию меню и клиентский экран.
8. Для mixin-изменений проверять правильный `mixins.json`, refmap, target-класс и совместимость с конкретной версией AE2.
9. Не редактировать вручную файлы в `src/datagen/generated`; менять provider/datagen-код и запускать `DataGen`.
10. После изменений запускать минимальную релевантную проверку Gradle; при изменении Java или ресурсов предпочтительно проверять `build` либо соответствующую run-задачу.
11. Не добавлять новые зависимости, пока не проверена возможность использовать уже подключённые Forge/Minecraft/AE2 API.
12. Все неизвестные игровые решения, названия контента и ожидаемое поведение сначала фиксировать вопросом, а не угадывать.

## Рабочий процесс Claude

1. Изучить относящиеся к задаче разделы `AI_CONTEXT.md`, `ARCHITECTURE.md` и `DEVELOPMENT.md`.
2. Сформулировать короткий план и перечислить предполагаемые файлы.
3. Найти существующие паттерны и выполнить минимальные согласованные изменения.
4. Запустить минимальную релевантную Gradle-проверку: для Java и связанных ресурсов — `build`, для datagen/provider — `DataGen`, если это требуется изменением.
5. Проверить итоговый diff и убедиться, что сторонние незакоммиченные изменения не затронуты.
6. Кратко отчитаться о результате без создания коммита.

## Текущий фокус проекта

Проект развивает IndustrialTech для Minecraft 1.20.1 на Forge 47.4.10. Равноправные направления — AE2 storage/crafting, crafting/ore-контент и клиентский UI/blur. Выбор приоритета зависит от конкретной задачи пользователя.
